# SPEC-008: Distribution

**Milestone**: M25 · **Status**: implemented; everything that needs a pushed tag is a manual check (docs/RELEASING.md) · **ADR**: [0033](../adr/0033-distribution-channels.md)

sciart 1.0 is installed four ways: a release binary (by hand or through the installer
script), a conda package for pixi, `cargo install`, and a Homebrew tap. One version number
feeds all of them, a release can be verified by whoever installs it, and nothing is
published without a maintainer's approval.

- **DIST-R1** One version: `workspace.package.version` in the root `Cargo.toml` is the only hand-edited version of the `sciart` crate. `pixi.toml` carries no version of its own; the conda recipe takes it from `SCIART_VERSION`; on a tag build the tag equals `v{version}` and `CHANGELOG.md` has a `## [{version}] - YYYY-MM-DD` heading. `scripts/release_check.py` enforces this (`--tag <name>` in the release workflow). `scripts/bump_version.py <sciart-version> <internal-version>` writes both version streams and every lock file in the repository that names a sciart crate (the workspace's, `fuzz/`'s and `web/`'s).
- **DIST-R2** `sciart -V` prints `sciart X.Y.Z`. `sciart --version` adds ` (<12-hex commit> <target triple>)` when the build was given `SCIART_GIT_SHA`, and nothing more otherwise (a crates.io build has no commit). The text comes from a pure `version_text()` that is unit-tested.
- **DIST-R3** Published crates: `sciart` and the eleven crates it needs. `sciart-testalloc`, `sciart-qa`, `fuzz/` and `web/` are never published. The internal crates share one `0.x` version of their own and are pinned from the workspace with `=`, so a given `sciart` release always builds against exactly the internals it was tested with. Each internal crate has its own `README.md` and a crate-level doc notice, both saying it is internal, carries no semver promise and that `sciart` is the supported entry point; its `description` starts with `Internal:`; it has no keywords or categories. The docs.rs metadata of `sciart` never enables `mouse`. `scripts/release_check.py` enforces this.
- **DIST-R4** `cargo publish --workspace --dry-run --locked` passes, in dependency order (core, shared, the five scene crates, generators, render, keepawake, capture, sciart). Every `.crate` file is at most 1 MiB: internal crates exclude `tests/`, `benches/` and `examples/`. The `sciart` crate ships `LICENSE`, `README.md` and `CHANGELOG.md`. `pixi run rs-package-check` runs the dry run and `scripts/release_check.py --crates` checks the sizes and contents. The real publish (DIST-R10) uploads one crate at a time in that order and skips a version that is already on the index, so a run that failed half-way can be run again; a published version can be yanked but never replaced.
- **DIST-R5** Release builds: the release workflow builds the six targets of TEST-R13 with `--release --locked` and default features (`record` on, `mouse` off); the Linux gnu targets build on the oldest supported runner image (`ubuntu-22.04` and `ubuntu-22.04-arm`) so the binary needs glibc 2.35 or newer, and the macOS targets on `macos-15`. Every job names an explicit image from the list of supported images (`RUNNER_IMAGES` in `scripts/tooling_check.py`, TEST-R13). Each artefact is `sciart-{version}-{target}.tar.gz` with the binary, `README.md`, `LICENSE`, `CHANGELOG.md`, the bash, zsh and fish completions and `sciart.1`, the last two generated by the built binary (CLI-R17). Every binary that can run on its runner is smoke-tested: `--version` matches the tag and `list --json` parses. `[package.metadata.binstall]` reproduces these names. `scripts/release_check.py` checks the workflow and the metadata.
- **DIST-R6** Verifiable: one `SHA256SUMS` file covers every release asset; each tarball, `install.sh` and `SHA256SUMS` itself have a build-provenance attestation; binaries are built with `cargo auditable` so their dependency list can be read back. Attestations are signed for public repositories only, so a pushed tag in a private repository fails in the first job, before anything is built, and a manual run in a private repository skips the attestation step with a notice and runs everything else. Every tool-install step names its tool: a pinned install action without one installs nothing. Every action a workflow uses is pinned to a full commit SHA with its version in a comment, in every file under `.github/workflows/`, and comes from an owner on the checker's allow-list. `scripts/release_check.py` checks the workflow's steps and permissions and the pins.
- **DIST-R7** `packaging/install.sh` is POSIX sh and shellcheck-clean. It detects the OS and architecture (on Linux, gnu when glibc is 2.35 or newer, else musl; under Rosetta the arm64 build), validates `--version <v>` (letters, digits, dots and hyphens only, starting with a digit, no `..`) before any request, downloads the tarball and `SHA256SUMS` over https (TLS 1.2 or newer, https-only redirects) for that version or the latest release, verifies the checksum on both paths, runs `gh attestation verify` when `gh` has that command and is signed in (otherwise it says so and relies on the checksum; a failed verification is fatal), and installs to `${SCIART_INSTALL_DIR:-$HOME/.local/bin}`. It refuses: an unsupported OS, a 32-bit machine or a 32-bit userland, a missing checksum tool, a checksum mismatch, a URL that is neither https nor a local `file://` mirror, running under sudo, and overwriting a file that is not a sciart binary without `--force`; it never edits shell start-up files and removes its temporary files on failure or interrupt. It knows a sciart binary by `Real-time generative science`, the start of the command-line description that the 1.0.0 binaries and the later ones (WEB-R9) share, so both are upgraded in place; the installer check upgrades a binary with each wording. `scripts/installer_check.py` runs it against a local fixture release, a tampered checksum on the versioned and on the latest path, faked platforms (among them glibc 2.34, a 32-bit userland and Rosetta) and hostile `--version` values, and checks the download flags. The documented one-line command (`curl … | sh`, in the README, the installer's header and the built site) follows redirects (`-L`), because the release host redirects `releases/latest/download/`, and keeps `--proto '=https'`, `--tlsv1.2`, `-f` and `-S`; the installer check (and the site check for the site) enforces it and runs its curl flags against a fixture host that redirects the same way.
- **DIST-R8** `packaging/conda/recipe.yaml` builds the package `sciart` with rattler-build for `osx-arm64`, `osx-64`, `linux-64` and `linux-aarch64`, bundles the third-party licences, and tests `sciart --version` and `sciart list`. `pixi run rs-conda-build` builds it locally for the host platform; the upload to the channel happens only in the publish stage (DIST-R10). `scripts/conda_build.py` refuses a tree with uncommitted changes unless `--allow-dirty` is given. `scripts/release_check.py` checks the recipe.
- **DIST-R9** The Homebrew formula is rendered by `scripts/render_formula.py` from `packaging/homebrew/sciart.rb.in` and a `SHA256SUMS` file: URLs for both architectures on macOS and Linux, installing the binary, the man page and the completions, with a `test do` that checks `--version`. The version written into the formula is validated as a semantic version first. `scripts/release_check.py` renders it from a fixture and checks the result.
- **DIST-R10** Nothing irreversible happens without a maintainer's approval. A pushed tag builds everything and creates a **draft** release. Its notes are the version's `CHANGELOG.md` section (`scripts/release_check.py --notes`) with every relative link made absolute and pinned to the tag (`<repository>/blob/v<version>/<path>`, the repository taken from the workspace manifest), since a relative link is dead on a release page. Publishing the draft starts a second workflow whose crates.io, conda-channel and Homebrew-tap jobs run in a `release` environment that requires a maintainer's approval. The hosting service creates a missing environment, without reviewers, the first time a job names it; so a first job outside the environment reads the environment's protection rules, every publish job needs it, and on a release event it fails unless the environment requires reviewers (a manual rehearsal only reports what it found). CI never creates or moves a tag (ADR-0024). `scripts/release_check.py` reads both workflows as data and fails when: a `cargo publish` without `--dry-run` sits outside the gated publish step; the publish gate is anything but the release event; a secret is set at job or workflow level instead of on the one step that needs it; a job's `permissions` exceed its allow-list; the chain build → package → release is broken; the tag check, the installer check or the smoke test is missing or cannot fail the job; or a `run:` script interpolates `github.event.*`. Both workflows have a concurrency group, every checkout sets `persist-credentials: false`, the release workflow restores no build cache, and each publish job can be run again after a partial failure.

Manual after a release (ROADMAP): `gh attestation verify` on a downloaded tarball, and an
install on a clean machine through each channel.
