# SPEC-009: Showcase, web gallery and docs site

**Milestone**: M25 · **Status**: WEB-R1/R2 (showcase) implemented; WEB-R3..R8 (web gallery, docs site) in progress · **ADR**: [0034](../adr/0034-web-gallery-and-docs-site.md)

The README, the gallery and the docs site show the art moving. Every animated capture is
recorded from the binary, from a manifest, so it can be regenerated and never drifts from
what the program draws.

- **WEB-R1** (M25) Showcase manifest: `docs/showcase.toml` lists the animated captures. Each entry has an `id`, the scene name, seed, size in cells, `start` and `seconds`, fps, theme, the output path under `docs/media/`, `alt` text, and an optional `readme` placement (`hero` or `grid`; absent means gallery only). Every clip is produced by `sciart record` with exactly those parameters. The parameters each clip was recorded with are written beside the clips (`docs/media/showcase.lock`); a clip whose manifest entry differs from its lock entry is stale. `pixi run rs-showcase` records the missing and the stale ones (and all of them with `--force`, which a change to a scene's look calls for). No clip is edited by hand or captured by another tool. A GIF clip is at most 1.5 MB and the whole set at most 16 MB (1 MB = 10⁶ bytes). The set covers at least 12 scenes from at least 8 categories and includes the thread idiom (a GEN-R25 scene), the orbital-thread stipple idiom (a GEN-R26 scene) and a half-block field scene (a scene on neither list whose source draws with `raster::Pixels`).
- **WEB-R2** (M25) `scripts/showcase.py --check` (`pixi run rs-showcase-check`, in `rs-ci` and CI) fails when a manifest clip is missing, stale (WEB-R1) or not a GIF with at least one frame; a file under `docs/media/` is neither a manifest clip nor the lock; a clip or the set is over its size limit; a manifest scene is not registered; the coverage of WEB-R1 is not met; `README.md` or a generated docs page references an animated image that is not a manifest clip, wherever it lives and however the tag is written, or any image that does not resolve to a file; or the animated section of `docs/GALLERY.md` differs from what its generator writes. `README.md` shows the manifest's one hero clip and every grid clip (at least eight), each with alt text that contains the scene name and says what the clip shows; `docs/GALLERY.md` has an animated section, written by its generator, with every clip.
- **WEB-R3** (M25, ADR-0034) Scenes in the browser: `web/` holds the crate `sciart-web`, outside the workspace like `fuzz/`, which builds for `wasm32-unknown-unknown` and exports the player as plain functions with no imports, which `site/static/player.js` wraps in a `Player` class: `new(scene, columns, rows, seed)`, `advance(seconds)`, `resize(columns, rows)`, `frame(theme)` returning RGBA pixels at 8×16 px per cell, and `scenes()` returning the same JSON as `sciart list --json` (CLI-R16). It has no terminal, no clock and no global RNG: time comes from the page's animation frame and is turned into fixed 1/60 s steps by the rule of LIB-R5. The crate also builds natively, where a test proves that a `Player` frame equals the capture renderer's pixels for the same scene, seed, size and time. The crates it needs build for the browser without `crossterm`, the image encoders or an operating-system RNG; `pixi run web-build` builds the module, and CI builds it on every push. `pixi run web-smoke` (in CI) runs the compiled module outside a browser: `scenes()` lists exactly the registered scenes, and every scene is created, advanced one second and returns a frame of `columns·8 × rows·16 × 4` bytes that is not blank.
- **WEB-R4** (M25) Weight: the compiled module is at most 3 MiB before compression and the page needs nothing else to play a scene. `scripts/site_check.py` enforces the budget, which may only be lowered without a spec change.
- **WEB-R5** (M25, ADR-0034) The site: `pixi run site-build` writes a static site to `site/dist/` from three sources and nothing else: the user guide in `docs/guide/` (installing, running, keys, configuration, scripting with `--for`, `frame` and `while`, recording, the library), built as a book by the site generator, in the order `docs/guide/chapters.toml` gives; the gallery, generated from the scene registry, the stills and the showcase manifest (WEB-R1), with one entry per registered scene; and the live player. The player starts paused when the visitor prefers reduced motion, can be driven from the keyboard while focus is inside it (a key never overrides a focused control's own action, and no key is taken elsewhere on the page), lets the visitor pick the scene, theme and seed, and falls back to the recorded clips where WebAssembly is unavailable or the module fails at any point. Every image has alt text.
- **WEB-R6** (M25) Self-contained: the built site loads no script, style, font, image or frame from another origin and contains no analytics or tracking. `scripts/site_check.py` scans `site/dist/` and fails on any such reference, however it is written: an attribute, a style rule in any letter case, `image-set`, the player's data (its module path is relative), a `<base>` element, a `refresh` redirect, `ping`, an import map or an SVG reference. The site's scripts fetch and import only literal relative paths; a computed address fails the check. Ordinary links in the text are allowed.
- **WEB-R7** (M25) Truthful: `scripts/site_check.py` fails when a registered scene is missing from the gallery, an internal link or asset does not resolve, the install commands on the site differ from the README's `Install` section, or the guide names a subcommand, a flag or a flag value the binary does not have (checked against `sciart completions` output).
- **WEB-R8** (M25, ADR-0034) Publishing: `.github/workflows/pages.yml` builds the site and deploys it to GitHub Pages only on a manual run from the default branch or a published release, through the `github-pages` environment; a push never deploys, and a manual run from another branch builds without deploying. `scripts/tooling_check.py` checks the triggers and the environment.
